# 05 — 為什麼這樣架：引擎 vs 工具

整個 SOP 最關鍵的一個判斷，弄懂它你就不會再走彎路。

## 核心原則：Muse 是「工具」，不是「引擎」

| | 當「引擎」（model）✗ | 當「工具」(MCP/CLI) ✓ |
|---|---|---|
| 誰送 prompt | opencode 把整套 system prompt + 工具表 + 歷史一次倒進去 | 你挑一個「小、明確」的任務丟進去 |
| context 量 | 可達 **60~70 萬字** | 一句話 |
| 結果 | **灌爆瀏覽器網頁窗口**，provider-error / 卡死 | Muse 正常回話 |
| 心智 | 我是一個 AI 引擎，要處理巨人 context | 我是「駕瀏覽器送一句話的工具」 |

**原因**：Muse 沒有公開 API，是靠一支真實瀏覽器網頁在跑。opencode 是 agent runner，每次 request 一定把整包 context 一起倒進來；這整包會經 shim 餵進瀏覽器 `Muse 網頁版`，窗口直接被塞爆卡死。**它本質是「一對一聊天的引擎」，不是「扛長 context 的 agent model」。**

## 正確的兩階段（一個 turn 內完成）

不需要養一支獨立員工 agent、也不需要兩個模型分「腦」和「發電機」——任何一個穩定 agent 在**自己的 turn** 裡：

1. **發送**：把一句小 prompt 送給 Muse（吃免費額度）。
2. **拍照**：讀瀏覽器真渲染的回覆來驗貨（`muse_read_last` / `muse_dump_dom`，或截圖存證）。

完事。deepseek 腦 + 瀏覽器是**一體**，不分家 → 就沒有「第二顆腦死掉」的事。

## 為什麼「養一支獨立員工」是畫蛇添足（實測結論）

我們一開始建了「Muse 打工仔」獨立 agent（deepseek + Muse MCP），結果：
- 它的 engine 選 muse-local → 灌爆浏覽器（見 docs/08 死路二）。
- 後來換 deepseek → 那顆「另開的 agent loop」自己也常 `OpenCode 停止響應`，而且手上的 Muse MCP 工具常常沒注入。
- **結論：白養了一支會死的鏈。** 真正白嫖的機制只有「駕瀏覽器送一句話」，不需要第二顆腦。

## 驗收判定（信真值，不信自述）

- 判引擎通不通：**看引擎 log 有無出現請求**，不聽 agent 說「我跑 deepseek」。
- 判瀏覽器真回話：**親手駕一下看回覆文字**，外部真值。
- 判注入成不成：agent 說「我有 muse」不可信，看它**真的能呼叫**並拿到回覆。
